# Putting this package on GitHub and getting a DOI

Written for someone who has not used GitHub before. Follow it in order.
Total time: about 40 minutes, most of it waiting for uploads.

You do **not** need to install anything or type any commands. Everything below
is done in a web browser.

---

## Before you start: what goes up, and what does not

**Do not upload the whole folder.** Six things must stay out, each for a
reason. The `.gitignore` file in this package lists them, but if you upload by
drag-and-drop that file cannot protect you — you must simply not drag them.

### KEEP OUT — six items

| Leave out | Why |
|---|---|
| `data_raw/20251231_NGPL.pdf` | Government document. Redistribution terms not stated. `scripts/00a_fetch_source.py` downloads it and checks it is the exact right one. |
| `data_raw/legacy_v0/20251231_NGPL.pdf` | A duplicate of the same file. |
| `data_raw/external/gazetteer/` (both files) | `IN.txt` is 69.6 MB. GitHub warns above 50 MB and refuses above 100 MB. `scripts/00b_fetch_gazetteer.py` downloads it. |
| `gis/osm_pipelines_raw.geojson` | Made from OpenStreetMap. OSM's licence has a "share-alike" rule: republish OSM-derived data and that rule spreads to everything around it. Keeping it out keeps your data licence clean. |
| `data_processed/osm_pipeline_survey.csv` | Same reason. |
| `data_processed/facility_candidates.csv` | Same reason. |

None of this harms reproducibility. Every excluded file is regenerated by a
script that is included.

> **A caution I should be plain about.** The OpenStreetMap share-alike question
> is a genuine legal grey area and I am not qualified to settle it. A summary
> table of counts is probably not a "derived database" in the licence's sense,
> but "probably" is not good enough to build a publication on. Leaving all three
> out costs you nothing and removes the question. If your institution has
> someone who advises on data licensing, this is the one thing worth asking them
> about.

### KEEP IN — everything else

- `data_processed/` — the 15 remaining CSV files. **This is the dataset.**
- `gis/pipeline_routes.geojson`
- `metadata/` — data dictionary and changelog
- `scripts/` — all 18 scripts
- `data_raw/legacy_v0/` — the three small files (not the PDF). The validators
  need these; they are the independent cross-check.
- `data_raw/external/SOURCES.md`
- `README.md`
- The six new files in this package: `.gitignore`, `LICENSE`,
  `LICENSE-DATA.md`, `CITATION.cff`, `requirements.txt`, and this file.

### Also keep out: the paper

`PAPER_DRAFT_v2.docx` and the other manuscript files are not part of the data
package. Keep them in a separate folder on your laptop. `.gitignore` already
excludes them.

## Step 1 — Make a GitHub account

Go to **github.com** and sign up. Free. Use an email you will keep.

Pick a username you are happy to see in a published paper. It becomes part of
your repository's web address forever.

---

## Step 2 — Make an empty repository

1. Click the **+** at the top right → **New repository**.
2. **Repository name:** `ngpl-india-network` — exactly that, to match the paper.
3. **Description:** paste this:
   *A provenance-separated reconstruction of India's authorised natural gas
   transmission network, built from the PNGRB register.*
4. Choose **Public**. It must be public for Zenodo to see it.
5. **Do not tick** "Add a README file", "Add .gitignore" or "Choose a license".
   You already have all three, and ticking them creates conflicts.
6. Click **Create repository**.

You now have an empty repository and a page that says "uploading an existing
file". Leave that page open.

---

## Step 3 — Upload the files

Click **uploading an existing file** on that page.

**Upload in four goes, not one.** GitHub's drag-and-drop is unreliable with
many nested folders at once, and doing it in pieces makes mistakes easy to see.

**Go 1 — the loose files at the top.** Drag these seven from your
`ngpl-india-network` folder:
`README.md`, `LICENSE`, `LICENSE-DATA.md`, `CITATION.cff`, `requirements.txt`,
`GITHUB_SETUP.md`, `.gitignore`

In the box at the bottom write: `initial commit: documentation and licences`
Click **Commit changes**.

> If `.gitignore` will not drag because Windows hides it: in File Explorer,
> View → tick **Hidden items**, then drag it.

**Go 2 — the scripts.** Click **Add file** → **Upload files**, and drag the
whole `scripts` folder in. Commit message: `build and validation scripts`.

**Go 3 — the data.** Drag the whole `data_processed` folder, then **delete the
three OSM files from the list before you commit** — GitHub shows you the file
list and lets you remove entries. The three are `osm_pipeline_survey.csv`,
`facility_candidates.csv`, and note that `osm_pipelines_raw.geojson` is in the
`gis` folder, not this one.
Also drag `metadata` and `gis` (from `gis`, only `pipeline_routes.geojson`).
Commit message: `dataset, metadata and reconstructed geometry`.

**Go 4 — the legacy files.** Make the folders by typing the path. Click
**Add file** → **Create new file**, and in the name box type:

```
data_raw/legacy_v0/README.md
```

Typing `/` creates the folders. Put this in the body:

```
Superseded working files, retained so the correction history can be verified.
Do not use these as data. metadata/changelog.csv records what was wrong with them.
The source register PDF is not stored here; scripts/00a_fetch_source.py fetches it.
```

Commit. Then **Add file** → **Upload files**, navigate into that folder, and
drag the three small legacy files. Do the same for
`data_raw/external/SOURCES.md`.

---

## Step 4 — Check what you uploaded

On your repository's front page, confirm:

- [ ] The README displays, with its tables.
- [ ] There is **no** `.pdf` anywhere.
- [ ] There is **no** `IN.txt`.
- [ ] `data_processed/` has **15** CSV files, and none of them starts with
      `osm_` or `facility_`.
- [ ] `gis/` has **one** file only.
- [ ] `scripts/` has 18 files.
- [ ] GitHub shows a licence in the right-hand panel.

If a wrong file went up: open it, click the **bin icon**, commit. It is gone
from the current version. It stays in the history, which matters only if the
file was confidential — none of these are.

---

## Step 5 — Connect Zenodo

1. Go to **zenodo.org**.
2. **Sign up → Log in with GitHub.** Use GitHub; do not make a separate
   account, or the automatic link will not work.
3. Allow Zenodo the access it asks for.
4. Top right, your name → **GitHub**.
5. Find `ngpl-india-network` in the list and **flip its switch to On**.

If it is not listed, click **Sync now**. It can take a minute.

**This does nothing yet.** It only tells Zenodo to watch for a release.

---

## Step 6 — Make a release, and get the DOI

1. Back on GitHub, on your repository's front page, look at the right side for
   **Releases** → **Create a new release**.
2. **Choose a tag** → type `v1.0.0` → **Create new tag**.
3. **Release title:** `v1.0.0 — first public release`
4. **Description:** paste this:

   ```
   Dataset and code accompanying the manuscript submitted to the
   International Journal of Critical Infrastructure Protection.

   99 authorised pipelines, 37 in analytical scope, 27 in the node-edge graph.
   215 automated validation checks; 57 mutation tests; five closure proofs
   against subtotals printed in the source register.

   The source register and the GeoNames gazetteer are not redistributed;
   scripts/00a_fetch_source.py and scripts/00b_fetch_gazetteer.py retrieve them
   and verify them by checksum.
   ```

5. Click **Publish release**.

Wait two or three minutes, then reload your Zenodo **GitHub** page. Your
repository now shows a **DOI badge** — a grey-and-blue label reading something
like `DOI 10.5281/zenodo.1234567`.

**That number is what your paper needs.**

---

## Step 7 — Put the DOI in four places

Search the manuscript for `[REPOSITORY DOI PENDING]`. It appears **four**
times:

1. Section 1, contribution 1
2. Data and code availability
3. Reference [18] — the dataset
4. Reference [19] — the software

Also update, in the repository itself:

- `CITATION.cff` — the `doi:` line and the `repository-code:` line
- `LICENSE` — replace `[AUTHOR NAME]`
- `CITATION.cff` — the author block and your ORCID

Commit those edits, then make a **v1.0.1** release so Zenodo's copy matches.

> Zenodo gives you two DOIs: one for **v1.0.0** and one **concept DOI** that
> always points at the newest version. **Use the concept DOI in the paper.**
> Zenodo shows it as "Cite all versions". It will not go stale when you release
> again.

---

## Step 8 — One last check

Ask someone who has never seen this project to do the following, with no help
from you:

1. Open the GitHub page.
2. Read only the README.
3. Follow section 10 of it.
4. Try to produce `pipeline_master.csv`.

Whatever they get stuck on is what a reviewer will get stuck on. Fix that, then
submit.

---

## If something goes wrong

**"File too large."** You dragged `IN.txt`. Remove it from the list.

**"Repository not showing in Zenodo."** Your repository must be Public, and you
must have logged into Zenodo *with GitHub*. Click Sync now.

**"No DOI after the release."** The Zenodo switch must have been On *before*
you published the release. Turn it on, then publish a fresh release, `v1.0.1`.

**"I uploaded the PDF by mistake."** Delete it from the repository. If the paper
is not yet submitted, no harm is done. Note that it remains in the repository's
history; to remove it completely you would delete the repository and start
again, which at this stage costs you twenty minutes.
